段号驱动与状态机推进方案

把多段攻击的"段号"判定从 Animation Event 反射回调迁移到 FSM.OnUpdate 主动推进 + CSV 配置驱动,解决 10×5×5 规模化场景下的工作量爆炸问题。

版本 v1.0 日期 2026-09-12 作者 蔡振立 状态 待评审落地
⚠ 现状同步（2026-09-15）：本文是 2026-09-12 的方案稿，落地之后实现又演进过多轮。 第 5 节代码、第 6 节 CSV 字段已按 2026-09-15 现状同步；工作量对比、落地步骤按原文保留，作为决策记录。
与原文的关键差异：
① _leftIdle / _castFired 两个 bool → _phase 枚举 + _castCursor 特效游标；
② PlayCastEffect() 无参版 → PlayCastEffect(int effectIndex)，时机改由 CSV CastEffectTimings 显式给出（不配就不播）；
③ CastEffectIds 列已删除，出手特效 id 的唯一来源是 AttackEffectID（列 22）；
④ CombatUnitController.GetWeaponAnchor() 已删除，绑点由 EffectManager 通过 EffectDot + BindName 自行解析；
⑤ 特效三问（播几个 / 何时播 / 播哪个 id）已全部下沉到 SkillData。
完整最新链路见 《战斗框架全链路与数据流转》。

1. 背景与痛点

当前战斗框架的"段号判定"完全依赖 Animation Event 在动画时间轴上手动绑定回调函数 OnSkillCase,通过反射机制触发 C# 逻辑(段号自增、伤害判定、特效播放)。

在 10 个玩家 × 5 个技能 × 5 段 的规模下,需要为每个攻击动画的每个段单独绑定 Event:

  • 总工作量: 10 × 5 × 5 = 250 段 × 2 个 Event(出手 + 判定)= 500 个 Animation Event
  • 修改时机: 必须重开 FBX,拖动 Event 到新帧
  • 新人接入: 每加一个角色都要重复一遍手工配置
  • 学员上手: 必须懂 Animation Event 反射机制、C# 字符串签名匹配
核心矛盾:Animation Event 是资产层的手动配置,在规模化场景下不可维护。

2. 核心方案

用 FSM 状态机主动推进 替代 Animation Event 被动反射,段数与时机由 CSV 配置 驱动。

三句话总结

  1. 动画师 只做"漂亮的攻击动画",不绑任何 Event
  2. 状态机 在 AttackState.OnUpdate 每帧检查 AnimatorStateInfo.normalizedTime,按 CSV 里的 SegTimings 数组推进段号
  3. 特效 / 伤害 在段号触发点直接调 C# 方法,不经过反射

方案对比

维度旧:Animation Event 反射新:FSM 推进 + CSV 驱动
动画师工作量500 个 Event 绑定0 个(只做动画)
新角色接入每个新角色重复 25 次 Event 绑定只配状态名一致即可
改时机重开 FBX 拖 Event改 CSV 一字段
段数调整删/加 Event + 改 C# 数组只改 CSV
新人上手门槛理解反射 + 字符串签名看懂协程 / 状态机即可
Debug 可观测性依赖 Console 日志每帧断点 / 日志直接打
动画速度变化需要动画师手动同步 Event 帧normalizedTime 自动适应

3. 时序设计

刀光(出手)和火花(判定)必须同帧,但刀光是"挥刀过程"的持续视觉,火花是"打击瞬间"的爆发视觉——它们应该挂在不同物体上:

核心原则:刀光是挥刀的伴生视觉(过程),火花是打击的瞬间表现(结果)。两者挂在不同物体,但触发时机相同 — 这才是"打到了"的视觉传达。

4. FSM 推进流程

把段号推进逻辑放进 AttackState.OnUpdate,与现有"等动画播完回 Idle"逻辑同处,生命周期完全由 FSM 管理。

5.1 AttackState 改造 (CombatStates.cs)

C# CombatStates.cs · 替换 AttackState 类 

private enum AttackPhase { WaitingForLeave, Playing }   // v5 P3：一维枚举取代 bool 二维判断
private const float LEAVE_IDLE_GUARD_SECONDS = 5f;

private AttackPhase _phase;   // WaitingForLeave → Playing
private float _elapsed;
private Skill _currentSkill;
private int _firedSegIdx;    // 已触发段数 == 下一段在 _segTimings 里的下标
private int _segCount;       // = BaseData.GetSegmentCount()（CSV SegCount 列）
private float[] _segTimings;
private int _castCursor;     // 特效轨道游标：已播数量 == 下一个待播下标（0-based）
private int _castCount;      // = BaseData.GetCastEffectCount()

public CombatState StateType { get { return CombatState.Attack; } }

public void OnEnter()
{
    _phase = AttackPhase.WaitingForLeave;
    _elapsed = 0f; _firedSegIdx = 0; _castCursor = 0; _castCount = 0;
    _currentSkill = null; _segCount = 0; _segTimings = null;

    // v5 P9：直接取 owner 当前选中技能（原为 context 传 skillId 再 GetSkill 线性查表）
    _currentSkill = Owner.CurSelectedSkill;
    if (_currentSkill != null)
    {
        _currentSkill.SetSkillCaster(Owner, Owner.m_Target);

        // v5 P6：段数来自 CSV 的 SegCount 列，不再用 SegTimings.Length 顶替
        _segCount = _currentSkill.BaseData.GetSegmentCount();
        _segTimings = _currentSkill.BaseData.SegTimings;

        // v5 P8：特效条目数 = min(有效特效 id 数, 时机数)，与段数无关
        _castCount = _currentSkill.BaseData.GetCastEffectCount();
    }
    else
    {
        // v5 P9 补偿：删掉 object context 后需显式告警，否则「空技能进攻击」会静默失败
        Debug.LogWarning("[AttackState] CurSelectedSkill 为空 → 本次不结算伤害与特效");
    }
}

public void OnUpdate(float deltaTime)
{
    // ① 起手守卫：等 Animator 真正离开待机才开始推进（★ 2026-09-22 抽出）
    if (!TryEnterPlaying(deltaTime)) return;   // 内含保险丝，超时 LogError 指名

    // ② 结束判定：动画播完、Animator 自动回待机 ⇒ 本轮结束
    if (TryFinishSkill()) return;

    // v5 P1：每帧只读一次 Animator 状态，两条轨道共用（native call 2 → 1）
    AnimatorStateInfo info = Owner.View.StateInfo;

    // ③ 特效轨道：时机来自 CSV 的 CastEffectTimings，与伤害段无关
    //    ⚠ 必须排在伤害之前：同帧跨过两点时先出特效再结算，避免「先掉血后见刀光」
    AdvanceCastEffect(info);   // 每帧最多一个（while → if）

    // ④ 伤害段轨道：时机来自 CSV 的 SegTimings
    AdvanceSegment(info);      // 每帧最多一段

    // ★ v5 P12：此处不再调用 DoAutoFight —— 攻击期间锁移动（详见主文档 STEP 03）
}
// ══ 上述四步在类里各有一个专属方法（2026-09-22 从 OnUpdate 抽出，逻辑逐行等价）══
//   TryEnterPlaying(deltaTime)            ① 起手守卫 + 保险丝 + 超时报错
//   TryFinishSkill()                      ② 动画播完 ⇒ 请求回 Idle
//   AdvanceCastEffect(info)               ③ 刀光：跨过配置时机即播，游标自增
//   AdvanceSegment(info)                  ④ 伤害：跨过时机点即结算一段

public void OnExit()
{
    _phase = AttackPhase.WaitingForLeave;
    _currentSkill = null;
    _segTimings = null;
}

5.3 Skill 播放出手特效 (Skill.cs)

C# Skill.cs · PlayCastEffect（2026-09-15 现状） 

// ★ v5 P8：Skill 只负责「拿到 id → 交给 EffectManager」
//   「播几个 / 何时播 / 播哪个 id」三问已全部下沉到 BaseData（SkillData）
public void PlayCastEffect(int effectIndex)
{
    if (m_SkillCaseter == null) return;

    // 1-based；无效 / 越界 / 该位为空 一律返回 0
    int castEffectId = BaseData.GetCastEffectId(effectIndex);
    if (castEffectId <= 0) return;   // 不退化到播第 1 个

    // 绑点由 EffectManager 通过施法者身上的 EffectDot 按 BindName 自行解析
    EffectManager.Instance.CreateEffect(castEffectId, m_SkillCaseter.transform);

5.5 UnitView / UnitHitReaction · 受击表现抽离 (v5 P13 · 2026-09-17)

此前受击链路的实现全写在 CombatUnitController 里：OnDamaged 同时负责扣血、 播特效、请求死亡状态、改仇恨四个毫不相干的职责；三个击退入口做的事完全一样却有着三套不同的防御判断。 现在按「单位认识谁」拆成两个组件，Controller 保留同名方法作为对外契约（Facade）， 所以 Skill.ImmedDamage、UnitBuffComponent 的调用点一行都没改。

组件回答的问题不能做什么
UnitView 「看起来发生了什么」—— Animator 参数读写、动画状态查询、特效创建、死亡表现 不持有血量/攻击力等业务数据，不做任何判断
UnitHitReaction 「受这一下要播什么、切什么状态」—— 扣血 → 受击特效 → 死亡判定 → 仇恨 → 控制态 不让 View 或 FSM 反向依赖它
Controller 血量真相源、索敌决策、FSM 桥接 不再直接摸 Animator

5.5.1 持有方式：为什么不用 AddComponent

这两个类不继承 MonoBehaviour —— 它们是 Controller 在 Start() 里 new 出来的普通 C# 对象， 经 View / HitReaction 两个只读属性向外暴露。状态机依旧写 Owner.View.Xxx， 所有既有调用点一字未改，变的只有「对象从哪来」。

C# CombatUnitController.cs · 由「挂载组件」改为「持有对象」 
// 改前：往单位 GameObject 上挂两个组件，再靠 Setup 补依赖
//   m_View        = gameObject.AddComponent<UnitView>();
//   m_HitReaction = gameObject.AddComponent<UnitHitReaction>();
//   m_HitReaction.Setup(this, m_View);   ← 漏掉这一步，编译期毫无痕迹

// 改后：构造即绑定，依赖直接进 readonly 字段

if (m_View == null)        m_View = new UnitView(this, m_Animator);
if (m_HitReaction == null) m_HitReaction = new UnitHitReaction(this, m_View);
  • 消灭「实例存在但依赖未注入」的窗口 —— UnitView(owner) 在构造时就取回 Animator， UnitHitReaction(owner, view) 在构造时就收下依赖，两个字段都是 readonly。 原先 AddComponent + Setup 两步式里，漏掉第二步要到 ApplyHit 才炸。
  • Inspector 与 prefab 保持干净 —— 单位身上不再多两个「看得见却无从配置」的组件， 也不存在「组件删了但 GUID 还留在场景里 → Missing Script」的隐患（已核验两份 GUID 在全部场景 / 预制体中零引用）。
  • 创建时机完全可控 —— 同步发生在 Start() 中、状态机注册之前，不再依赖 Unity 何时回调 Awake。
  • Animator 不重复获取 —— 宿主基类 MoveBaseController.Awake() 早已取好 m_Animator， View 直接沿用该引用。省一次查询倒在其次，真正要杜绝的是真相源分裂：若 Animator 将来改挂到子节点模型上， 基类的取法会跟着调整，而 View 自己那句 GetComponent 不会 —— 于是出现「Controller 认为有、View 认为没有」的偏差。
代价要说清楚：这两类对象无法在 Inspector 里展开调试 —— 想确认 Animator 有没有取到， 只能在 UnitView 里临时加日志。将来若需要响应 Unity 消息（例如 OnAnimatorIK）， 得由 Controller 手动转发一层。就这两个类目前的职责而言，都没有用到 MonoBehaviour 的任何能力， 所以这属于白赚 —— 去掉的是一个从未使用的基类。

public HitOutcome ApplyHit(CombatUnitController attacker, int damage, int hitEffectId)
{
    if (attacker == null || m_Owner.IsDead || m_Owner.CanbeAttack > 0) return HitOutcome.Ignored;

    m_Owner.Hp = Mathf.Max(0, m_Owner.Hp - damage);              // ① 先扣血
    if (m_Owner.Hp <= 0) { m_Owner.RequestState(CombatState.Dead); return HitOutcome.Dead; } // ② 死了不再加火花
    if (hitEffectId > 0) m_View.PlayEffect(hitEffectId);                    // ③ 再出画面
    if (m_Owner.m_Target == null) m_Owner.m_Target = attacker;            // ④ 死者不需要仇恨
    return HitOutcome.Normal;
}

public void ApplyHurt(CombatUnitController attacker, int hitType)
{
    if (attacker == null || m_Owner.IsDead || hitType <= BattleConst.HIT_TYPE_NONE) return;

    m_Owner.StartCoroutine(HitStopRoutine());   // ① 顿帧：只冻受击方
    m_View.PlayHit(hitType);                      // ② 受击动作
}

// ★ 这里刻意不写「打断攻击」：本方法对玩家与敌人对称生效，
//   一旦在这里 RequestState(Idle)，敌人技能只要配了效果 22，玩家的三连斩也会被同样打断。
//   「挨一刀就被打断」是玩法规则（霸体 / 韧性），应落在 FSM / Buff 的显式判定上。
// 顿帧令牌：连击时作废旧协程的「恢复速度」，避免第 1 段提前解冻
private IEnumerator HitStopRoutine()
{
    int token = ++m_HitStopToken;
    m_View.SetAnimatorSpeed(0f);
    yield return new WaitForSeconds(BattleConst.HIT_STOP_SECONDS);
    if (token == m_HitStopToken) m_View.SetAnimatorSpeed(1f);
}

参数：Die / Run / SkillId  →  + Hit(Trigger) + HitType(Int) + Move(Bool)   （共 6 个）

[SM] Base Layer
  Any   → Die              [Die==true]  ★ P15-fix：死亡入口，排 AnyState 首位且禁止自转
  Any   → Hit(SM)          [Hit]        ← 受击可覆盖当前动画（跑动 / 施法 / 受击中）
  idle  → Hit(SM)          [Hit]        ← ★ 插在 idle 转换列表的**第一位**
  idle  → Die              [Die==true]  ★ P15-fix：原为无条件脏边，现补条件
  idle  → Run_F / Down / FloatHit       （既有无条件出边，本次未动）
  Die   → idle             [Die==false] ★ P15-fix：不拦会形成死亡无限循环

[SM] Hit
  Entry → LightHit         [HitType Equals 1]
  LightHit  → idle         [ExitTime=1]
  ContiHit  → idle         [ExitTime=1]   ← 兜底状态原本无出边，进去会卡死，补安全阀
  （HeavyHit / FloatHit / Down / Dizzy / Frozen 等 9 段仍未接入，保持原样）
  • 为什么入口要做两条：idle 上挂着 4 条真正的无条件出边 （hasExitTime=0 且无条件的 Run_F / Down / FloatHit / Die）。Unity 对 「当前状态的转换」与「Any State 转换」谁优先没有公开保证，只建 Any State 有可能被无条件边抢掉。 所以把 idle → Hit 插到 idle 转换列表首位，再补一条 Any State 兜底 —— 两条保险并存。
  • 打断为什么最终回退：实现过一版（受击且处在 Attack ⇒ RequestState(Idle)），同日撤销 —— 这条管线对玩家与敌人对称生效，CSV 里有 37 个技能配了效果 22，敌人一旦使用它们， 玩家的三连斩会被同样打断。而「挨一刀就被打断」是玩法规则，应由受击方的霸体 / 韧性决定， 不该藏在通用受击表现里生效。将来要做，落点在 FSM 或 Buff 的显式判定。
  • 顿帧只冻受击方：攻击方的段号推进读的是自己 Animator 的 normalizedTime， 一起冻住会让三连斩卡段。另在 UnitView.PlayDeath() 首行恢复 speed = 1， 否则在顿帧窗口内死亡会「站着不动地死」。
  • 画面端仍只走 UnitView：Controller 与状态机没有新增任何一处直接摸 Animator 的代码。
本轮的取舍（用户 2026-09-18 拍板）： ① 受击不打断敌人攻击（实现后因对称性否掉，同日回退）；② 第 1 段不补配 Hure，所以三连斩第一刀只有掉血与火花、没有受击动作； ③ 受击不区分轻重 —— CSV 只表达「这一下有受击」，没有强度之分，因此统一按轻型处理， Skill.OnHure 是将来若新增强度列的唯一替换点；④ 本次范围 A+B，击退位移缓办。 动画层的 HitType 分流结构已就位，将来加一档受击只需：加常量 + 加一条 Entry 分支 + 加一条回 idle。

验证结论（2026-09-18 实测）：编译 0 Error 0 Warning；[SegEffect] 效果=[0,22] 99 条 ↔ [HitReact] 99 条严格 1:1；[HitEffectCalc] ↔ [HitEffect] 149 : 149 仍 1:1；Parameter 'Move' does not exist 告警消失（A 段补上了 Move 参数）。资源侧改动全部经 Assets/Tools/parse_animator.py 复验拓扑可 diff。

5.7 死亡链路修复 · Die 是 Bool，死亡动画从未播放 (v5 P15-fix · 2026-09-18)

上一节用 parse_animator.py 复验拓扑时顺带发现：敌人的死亡动画从来没播过。 这不是一处写错，而是三个病根叠在一起，且都不是本次 P15 引入的（迁移前就存在）：

#病根为什么致命怎么治
①Die 参数是 Bool（m_Type: 4），
而 PlayDeath() 写的是 SetTrigger("Die")		 对 Bool 参数设触发器既不生效也不报错 —— 静默失效， 日志里什么都看不出来 新增 WriteDeathParam()：先查参数真实类型再写值
②idle → Die 这条边没有条件，
却排在 idle 转换列表的末位		 前面 Run_F / Down / FloatHit 三条同样无条件且能命中 ⇒ 这条边从未生效过，死亡没有入口 给它补条件 [Die == true]，
并新增 Any State → Die 作真正的入口
③Die → idle 有一条 ExitTime 回边 就算真进了死亡态，播完也会被拉回待机；
与 ② 的新入口叠加 ⇒ 「死亡 → 回待机 → 再死亡」无限循环		 补条件 [Die == false]：死了就不再回待机
C# UnitView.cs · 按参数真实类型写死亡（★ 本次修复核心） 
private void WriteDeathParam()
{
    AnimatorControllerParameter p = FindParameter(BattleConst.ani_Die);
    if (p == null)      // 玩家 NYT.controller 根本没有 Die 参数
    {
        if (!_deathChecked) { _deathChecked = true;
            Debug.LogWarning($"[UnitView] {m_Owner.name} 没有 Die 参数 —— 无死亡动画"); }
        return;
    }
    _deathChecked = true;

    switch (p.type)
    {
        case AnimatorControllerParameterType.Bool:     m_Animator.SetBool(ani_Die, true); break;
        case AnimatorControllerParameterType.Trigger:  m_Animator.SetTrigger(ani_Die);      break;
        default: Debug.LogError($"Die 参数类型是 {p.type}，代码只支持 Bool / Trigger"); return;
    }
    Debug.Log($"[Death] {m_Owner.name} 写 Die({p.type}) = 死亡");
}
Animator GBL.controller · 死亡通路（P15-fix 后；parse_animator.py 可复验） 
[SM] Base Layer
  Any   → Die       [Die==true]   ★ 真正的死亡入口；排在 AnyState 列表首位、canTransitionToSelf=false
  idle  → Die       [Die==true]   ★ 原无条件脏边，已补条件
  Die   → idle      [Die==false]  ★ 拦掉「死亡 → 回待机」的回边

  ⚠ canTransitionToSelf 必须为 false：Any State 转换默认允许「目标就是当前状态」，
    不关掉的话死亡动画会在每一帧被重新进入，永远重播第一段。
  • 为什么做类型自适应而不是统一改一种：敌人 GBL.controller 与玩家 NYT.controller 是两套历史资产 —— 改资产要动 YAML 与全部旧分支，改代码只动一处。 类型查询的成本是每个单位一次（有缓存），可忽略。
  • Bool 而不是 Trigger 的好处：Bool 是持续为真的状态量，单位只要还存在， Animator 就一直知道「它是死的」—— 这正是 [Die == false] 这个出边条件能成立的前提 （Trigger 用完即清，回边条件会立刻为真）。
  • 为什么不动 idle 上 Run_F / Down / FloatHit 那几条脏边：它们今天仍然会抢在 idle 的所有后续转换之前， 但有 Any State 这条入口兜着，删除它们属于改变既有行为，不在本次范围。

验证结论（Play 实测）：新增运行时探针 DeathLinkProbe（#if UNITY_EDITOR，不进正式包）， 走真实路径 CombatUnitController.SetDead(true) → View.PlayDeath()， 之后每 0.4 秒采样一次 Animator 当前状态：8 次采样 inDie=True 全部成立、 Die=True、最终结果 [DeathDiag] 结论 PASS —— GBL(Clone) 进入并停留在死亡状态。 同轮 [HitReact] 51 条对应 [SegEffect] 效果=[0,22] 53 条 —— 差额 2 正是 死亡之后的两段（ApplyHurt 首行 IsDead 直接 return），契约未被破坏； [HitEffectCalc] ↔ [HitEffect] 78:78 仍 1:1，0 Error 0 Warning。

顺带修掉的工具缺陷：parse_animator.py 此前把 m_Type 当连续下标 ⇒ 4 被报成 Trigger（实际是 Bool），正是这个误报掩盖了本节的病根 ①。 参数类型映射是跳跃枚举：1=Float / 3=Int / 4=Bool / 9=Trigger。

9. 边界与保护

9.1 已知边界

场景行为保护机制
动画被 Stun / Knockback 中断AttackState 被打断,OnExit 清理字段FSM 自动管生命周期
