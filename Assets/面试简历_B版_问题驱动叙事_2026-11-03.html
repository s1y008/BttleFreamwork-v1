A 版 vs B 版

A 版＝职责与功能罗列，回答「我做了什么」，一页，投招聘平台用。

项目概览与当前架构

BttleFreamwork-v1 · 截至 2026-11-03
项目Unity 战斗框架 BttleFreamwork-v1（Unity 2023.2.20f1c1，单机，无 git）
我的角色架构演进主导 / 代码复核 / 排查与拍板 / 工程规范建设 / 教学化沉淀
规模53 个运行时 .cs、16 个 Editor .cs、7 张配置表（技能 236 行 / Warrior 21 / AttackNpc 1460 / Buffer 6 / Effect 4）、8 个编辑器文件
技术栈C# / Unity Animator / Newtonsoft.Json / Odin Inspector / ScriptableObject / IMGUI / ProfilerRecorder / 自研 UnitySkills HTTP 编译与 Play 验证链 / Python 改造与等价性脚本
分层架构状态机 FSM策略注册表 零 GC（readonly struct + in）配置驱动 弹道扫掠判定ICastClock 联网接缝Editor 工具链

架构思想：把四件事拆开，每件事只有一个真相源

① 输入→ ② 决策 WarrorController→ ③ 状态机 RequestState(Attack)→ ④ 时间推进 ICastClock→ ⑤ 结算 SkillHit(segIdx)→ ⑥ 效果注册表→ ⑦ UnitHitReaction.ApplyHit→ ⑧ UnitView / BuffSystem

收尾由三条独立路径谁先到谁触发（① 段数打完　② 动画播完，兜底 233 个 SegCount=0 的技能　③ 被打断，只回调不切状态）， _castFinished 保证只收一次。这三条路径是「一次按键无限连击」排查后的直接产物，见案例 04。

八层职责里最关键的契约

  • 效果系统三态：已实现执行 / 已知空桩静默 / 未知号报错；填桩必须从 KnownStubIds 移除
  • 状态实例与单位 1:1，共享必串台；切换入口只有 RequestState
  • 三层分工：UnitView（画面唯一出口）/ UnitHitReaction（受击编排）/ Controller（决策 + Facade），后两者是普通类
  • SegIdx 1-based 只在 Skill 内流转，对外唯一入口 SkillHit(segIdx)
  • 弹道不得持有 cast 上下文、结算器不得调 SkillHit（防无限发射）

我建的验证链（面试可直接讲）

  • 三链 1:1：[HitEffectCalc]↔[HitEffect]、[SegEffect]↔[HitReact]，差额只在死亡后出现
  • 判回归只看 Exception == 0，不看 Error 总数（LogError 按命中次数线性累加）
  • 等价性脚本：235 行 × 26 字段逐条全等、946 个单元格差异 0、2597 项行为输出逐条相同
  • 冒烟：58 项 / 76 条断言 / 11 项全过；HTML 必跑 smoke_html.js + check_html_tags.py

01 画面上多出一个特效：五轮假设全部落空，真凶是一行配置 id 方法论 · 最贵的一课 09-19▼
发生了什么
玩家 10003 三连斩，第二次施法时特效 #1 与 #2 在同一帧播出，画面上出现两个刀光。现象是视觉的，我当时手上有大量日志、没有截图。
怎么查（走错的路）
我把「画面上出现两个东西」自行翻译成「时序 / 并发问题」，此后连换五个技术假设，落地三个方案全部回退：
  • P17 查时序：实测稳态 31 轮 #1≈0.143 / #2≈0.333 / #3≈0.603，同帧连播 0 次；把 while 补播改 if + 加 [CastLag] 告警 —— 现象依旧。
  • P18 特效自动回收器：方向错 —— 存活时间估算把 lengthInSec: 2（其实只是发射窗口）当成粒子可见时长，实际可见 0.15~0.5 秒，高估约 10 倍。回退。
  • P19 清场重播 + 15 个粒子 stopAction 0→1：仍不是因。回退。
  • 最刺眼的一条：P18 的探针其实已经打出「实例 -19044 父节点跳变」，我把它当无关噪声跳过了。
换方法
我停下来不再猜，改按最笨的顺序重来：先要截图 → 枚举 Hierarchy 现场对象（几个 / 叫什么 / 挂谁身上 / 谁实例化）→ 反查配置 id 全量映射 → 最后才看时序。 复盘我给自己记了一句：仅靠日志分析视觉问题，等于自愿蒙眼。
根因
2003 撞车：10003 的「受击特效第 3 段」与「出手特效第 3 段」配了同一个 id；而池化 key 用的是 ResName 不是 id，每个 key 只留一个实例 ⇒ 玩家第三段刀光与敌人第三段受击火花是同一个 GameObject，父节点在 Atk3 ↔ GBL(Clone) 之间来回搬家。 EffectData 全表只有 3 行 —— 一次全量 grep 就能看出交集，我却没做。
怎么解决
改配置 id（2003 → 10003）消除了重叠，但换来「第三段受击特效彻底没了」 —— 肉眼只能看到「不重叠」，看不到「本该出现的没出现」。 于是补 SkillData.ValidateEffectIdContract：① 两列出现同 id 报错；② 引用 EffectData 不存在的 id 报错；③ 不做自动修正，加载期一次性指名。 另写 EffectSnapshotTool（导出场景特效对象清单 + 截图），把「我看不到画面」变成可观测。
沉淀
视觉排查五步法（截图 → 枚举对象 → 反查 id 全量映射 → 才看时序 → 用一条观测证明）； 配套三条：视觉描述不许自行翻译成技术假设、探针里「不该出现却出现了」的字段优先级高于自己的推理、交付前必须能指出「哪一条日志 / 哪张图证明假设成立」。 这条方法论后来在另外 3 次视觉问题里直接命中。
02 配了、写了、调了，什么都没发生，还不报错：静默失效的三种形态 fail-fast 设计 09-29 / 09-22▼
发生了什么
流血 Buff 配好了不扣血；某些效果号配了完全无反应；JSON 里改了值，进 Play 却像没改。三件事都不抛异常、不打 Warning。
怎么查
编译 0 Error → 查 Play 日志 → 逐层打点确认 AddBuff / ExecuteEffect 到底有没有被调用 → 再把配置表与 C# 成员做全量映射核对。 关键判断：「两套系统对不上」先查配置表有没有缺行，再怀疑代码架构（09-07 就吃过一次：Stunned / Silenced 两套控制互不认账，根因只是 BufferData.csv 缺两行）。
根因（三条独立）
  • BuffID 列为空 ⇒ 效果类遍历 0 次，既不挂 Buff 也不报错，全表 12 个技能踩坑。
  • 23 个效果号里 19 个是空桩，注册表直接跳过；175 个技能段配了这些号。
  • Newtonsoft 按「键名 ↔ 类的公开成员」取值：键名拼错、成员 readonly 或无 setter ⇒ 不报错、值直接丢失。
怎么解决
加载期 ValidateBuffBindings 指名报错；效果系统改三态（已实现执行 / 已知空桩汇总 / 未知号报错），并在编辑器里把未实现的 19 个标红、压到「── 未实现 ──」分隔条下； 配置列一律人工改、AI 只做契约校验 + fail-fast。
更关键的是删掉运行时兜底：原来 EnsureHitParams 会在运行时补 Animator 参数，Unity 对不存在的参数 SetXxx 只打 warning 不崩 —— 这个兜底不防崩溃，只把「资产漏配」伪装成「打了没反应」。改成构造期一次性 ValidateAnimationContract()，缺参数当场指名。
沉淀
铁律：资产契约优先，禁止为「资产不一致」写运行时静默降级。 另一个配套认知：稳定存在的 74 条 Error 全是配置层死配置（受击特效引用不存在的 EffectData id 56 条 / 出手 6 条 / BuffID 空 12 条）， 所以判代码有没有坏只看 Exception == 0，不看 Error 总数 —— 特效类 LogError 按命中次数累加，总数随战斗时长线性增长。
03 编译 0 Error，但三段技能永远只打第一段：一天推翻三次的段号驱动 顺着调用链查 09-11▼
发生了什么
3 段技能只识别到 segIdx=1；第二次施法段号跨释放累加成 1/2/3 → 4/5/6，每次命中把整个特效列表播一遍。编译全程 0 Error。
怎么查（三次推翻）
  • v1：把「每次都会调用的上下文设置函数」当成「新一轮的开始」—— SetSkillCaster 一次施法被调 3~4 次，每次都把段号归零。
  • v2：帧阈值语义漂移 —— 30 帧 ≈ 0.5s，而段间隔 0.6s = 36 帧 ⇒ 第 2/3 段全被误判成「新一轮」，退化成第 1 段。
  • v3：扫 110 个 AnimationClip 发现 events 字段为空就断言「永不回调」（字段为空 ≠ 没绑事件）； 又把 IdleState.OnEnter 当唯一重置点，顺着 RequestState 的调用方 grep 才发现全工程零处调 RequestState(Attack)，那是死代码。
根因
在动画控制器，不在代码：NYT.controller 的 Idle 状态挂着 SkillId == 10003 → Skill10003 转换， 动画播完 SkillId 残留 ⇒ 自动重放 ⇒ 段号跨释放累加。
怎么解决
重置职责精简到 1 道关（同一种职责留三处必然互相打架）； AttackState 改两段式 _phase = WaitingForLeave / Playing —— 因为 SetInteger 后 Animator 有 1~2 帧延迟（Idle 转换 m_ExitTime: 0.84）， 若进 Attack 当帧就判「播完了」，ResetSkillId() 会把 SkillId 清 0，那条还没生效的转换条件永久不成立，技能根本播不出来。 另外定死：不用「时间间隔 > 阈值」判新一轮（段间隔是玩法参数，会变）。
沉淀
Play 实测：[AttackState] seg=1/2/3 t=0.303/0.601/0.901，严格按 SegTimings 0.3/0.6/0.9 推进，连放正常。 两条纪律：① 编译 0 Error 只是及格线，涉配置 / 时序必须 Play 日志实锤 + A/B；② 验证设计假设要顺着调用方 grep，不能只读转换表。
04 按一次 A 键无限连击：不是 bug，是框架原本姿态被改了 语义还原 09-29▼
发生了什么
打开按键判断后，按一次 A 键，技能无限连击；硬控结束回 Idle 后，没按键也会自动再放一次。
怎么查
追 m_CurSelectedSkill 的生命周期，然后先还原框架原本的运行姿态： 原框架是自动战斗（Input.GetKeyDown 被注释、每帧无条件选技能 + 攻击）， 在那个姿态下「选中后常驻、不清空」本来就是对的。语义割裂点是「按键意图」被打开之后才出现的 —— 所以这不是写错了一行，而是两套语义没对齐。 顺带排掉两个易混点：IdleState.OnEnter 的 View.ResetSkillId() 清的是 Animator 参数，不是决策层对象（名字太像）； 以及绝不能在 AttackState 里统一清空 —— 敌人靠「技能不空」持续攻击，而 GetCanUseSkill() 全 CD 时返回 null，统一清空会让敌人站着不动。
根因
缺少「一次释放」的收尾语义；且转换表允许 Attack → Stun / Silence / Knockback / Dead， 被打断这几条只走 OnExit、不经过正常收尾 ⇒ 技能残留。
怎么解决
做成三条独立收尾路径，谁先到谁触发，_castFinished 保证只收一次： ① 段数打完（须同时满足 _castCursor >= _castCount，否则把「我们抢跑」误报成「配置错」）； ② 动画播完（兜底 233 个 SegCount=0 的技能）；③ 被打断，只回调、不切状态（OnExit 由 ChangeState 同步调用，此刻再 RequestState 属嵌套切换）。 回调 OnSkillCastFinished() 基类空实现（敌人零变化），WarrorController override 清空 —— 把「清决策层对象」放在 Controller，不在状态机。
沉淀
A/B 实锤：停用清空 30 秒 [SegEffect] 45 = 15 轮；启用后 3 = 1 轮。 改框架前先还原它原本的运行姿态 —— 很多「看起来是 bug」其实是语义漂移。
05 编辑器建好了，新增技能却仍是「死配置」：沿数据流追到最终消费者 数据驱动 10-12~14▼
发生了什么
技能编辑器已能可视化改 28 个字段，但我提出质疑：「新增一个技能还不是要手改配置？那编辑器的意义在哪？」
怎么查
从「加一行 JSON」出发，沿数据流一路追到真正消费这条数据的地方，挖出三层门槛：
① SkillData.json 加行→ ② 写进单位的 SkillArray→ ③ 玩家能选中释放
Warrior.cs:320 / AttackNpc.cs:291 的 m_SkillList 全部来自各自配置表的 SkillArray，不是从技能全表加载； 而 WarrorController.cs:74 硬编码 GetSkill(10002)。编辑器只覆盖第 ① 层，② 不做新技能就是死配置（打不出来也看不出来），③ 是运行时代码、编辑器改不了。
根因
「能配置」和「能生效」是两回事；数据驱动系统里，配置的最终消费者才是真相源。 另有两处隐性风险：CreateClone 若浅拷贝，6 个引用型成员会共享 ⇒「改新技能把源技能一起改了且不报错」； ConfigManager.GetAllSkillData() 不接纳新建项 ⇒ 未落盘的新技能 Refresh 后静默丢失。
怎么解决
新建向导（复制现有 / 空白模板、自动取最小未占用 ID、枚举选表现）+ 挂载层写两张单位表（21 + 1460 = 1481 个单位）+ 带搜索的挂载面板； CreateClone 用反射遍历 28 字段深拷贝、并对 List<int>[] 复制到第二层，写成冒烟断言而不只是注释； 新增行落盘时键顺序沿用第一行（否则一次保存产生上千行 diff）；「未落盘会丢」在向导 2 处 + 主窗口未保存清单标红共 3 处提示。
沉淀
编译 Tundra build success、error CS = 0；窗口打开零 Exception；冒烟 11 项全过且全程不写盘， 深拷贝实锤（改克隆第 2 段时机，源技能 0.6→0.6 纹丝不动）。 「能配置」≠「能生效」 —— 这条判断后来也用来否决了「纯配表实现突进接浮空」（效果号只在命中之后执行、无逐帧 tick）。

4.2 通用排查顺序

① 复述现象（不翻译）→ ② 枚举现场对象→ ③ 全量映射核对→ ④ 一条观测证明假设→ ⑤ 才看时序→ ⑥ 最小修复 + A/B→ ⑦ 固化成校验 / 冒烟 / 纪律

顺序的意义：③ 之前不动代码。9/19 的代价就是跳过 ①②③ 直接冲到 ⑤。

4.3 三条我不再妥协的判据

编译 0 Error ≠ 验证通过
涉配置 / 时序必须 Play 日志实锤 + A/B；回归顺序固定 stop → start_capture → play
不用 Error 总数判回归
特效类 LogError 按命中次数线性累加；只看 Exception == 0 + 三链 1:1
判死代码必须全量扫
grep 被 head_limit 截断误判 3 次；改用 scan_refs.py 排除 .bak / Library 全量输出

3 分钟自述稿（约 460 字）

【0:00–0:15 定位】　我主导过一个 Unity 战斗框架的完整演进：起点是 24 个 .cs、没有正式状态机、5 个核心方法全是空桩； 41 天后它变成配置驱动、单次技能 0 GC、带可视化编辑器的系统。我今天不想罗列功能，想讲过程中怎么定位那些不报错的故障。
【0:15–1:10 最贵的一课】　最值得讲的是 9/19：玩家三连斩第二次施法时画面上多出一个刀光。 我把它当成时序问题，连换五个假设、落地三个方案全回退；探针其实已经打出「实例父节点跳变」，被我当噪声跳过了。 后来我停下来改方法：先要截图、枚举 Hierarchy 对象、反查配置 id 全量映射，才看时序 —— 真凶是两列特效配了同一个 id（2003），而池化 key 用的是资源名不是 id，两个特效其实是同一个 GameObject 在来回换父节点。 那张配置表只有 3 行，一次全量比对就能发现。我复盘给自己记的是：仅靠日志分析视觉问题，等于自愿蒙眼。
【1:10–2:00 从事故长出来的方法】　这次之后我把问题分成五类，最危险的是「静默失效」：配了不生效还不报错。 所以定了一条铁律 —— 资产契约优先，不为数据不一致写运行时静默降级，一律改成加载期校验指名。 配套三条判据：编译 0 Error 只是及格线、不用 Error 总数判回归（它按命中次数累加）、判死代码必须全量扫而不是带 limit 的 grep。 另外我坚持「改框架前先还原它原本的运行姿态」—— 一次按键无限连击，根因不是写错代码，而是原本自动战斗的框架被打开了按键语义。
【2:00–2:45 结果】　架构上把数据、决策、结算、表现拆开，每件事只有一个真相源： 7 状态 28 条边的转换表资产化、23 分支 switch 改策略注册表、上下文改 readonly struct 做到 0 GC、 抽 ICastClock 给服务器留接缝。结果是 CPU −28%、GC 归零、CSV→JSON 迁移 2597 项行为输出逐条相同、编译与运行期 Exception 全为 0。
【2:45–3:00 收尾】　我最想强调的不是这些数字，而是每次修完都留下一道闸：校验器、冒烟脚本或一条纪律，让同类问题不再复发。

高频追问预判（左：面试官可能问 / 右：回答要点）

追问回答要点
为什么不用 git？接手时工程就没有版本库，是现状约束而非选择。替代方案：破坏性改动前物理备份 .bak.<日期>-<标签>（累计 221 份）、保存走 JSON 最小 diff（只替换改动的键、键顺序沿用首行）、每次改动配等价性脚本（2597 项行为输出逐条比对）。承认这是风险，不粉饰：所以我把「可回滚」做成了流程而不是工具依赖。
怎么证明「0 GC」不是测出来的假象？先讲踩过的坑：OverlapSphere 标定出「0 B/次」是假结论，因为单位是运行时克隆、Awake 阶段检测全空，Unity 返回的是缓存的空数组；测 GC 的探针也不能订阅 logMessageReceived（订阅行为自己制造 GC）。最终用 ProfilerRecorder 120 帧窗口比命中窗口与空闲窗口，差 <3%、低于测量噪声；再配合 [CastCtx] 21 == [SegEffect] 21 的构造次数打点交叉验证。
为什么禁止「静默降级 / 运行时兜底」？举两个实例：① Animator 参数漏配时运行时 EnsureHitParams 会补，Unity 对不存在的参数 SetXxx 只打 warning 不崩 —— 兜底不防崩溃，只把「资产漏配」伪装成「打了没反应」；② 2003 撞车改完 id 后重叠消失，但第三段受击特效也彻底没了，肉眼看不到「本该出现的没出现」。所以改成加载期一次性 fail-fast 指名，不做自动修正。
编译通过之后你还要做什么？三链 1:1 打点比对（[HitEffectCalc]↔[HitEffect]、[SegEffect]↔[HitReact]）、Exception == 0、A/B 对照实验、冒烟脚本；回归顺序固定 stop → start_capture → play（配置只在进 Play 时 Load 一次）。并且要核对 dll 的 mtime 确认真的编译了，别被「isCompiling」或历史陈旧错误骗了。
为什么否决 Timeline / 换 Animancer？三条硬约束：SegTimings 是归一化 0~1 的动画进度，Timeline 横轴是绝对秒，工程没有动画长度列；236 个技能里只有 3 个配了时间轴；而且会焊死 ICastClock 的联网接缝（服务器上没有 PlayableDirector）。所以自制三轨时间轴，只抄交互，约 250 行 Editor 代码、零运行时依赖。
如果重来一遍，你会先做什么？把「探测能力」建在改代码之前：① 配置 / 资产契约的加载期校验；② 场景对象与截图的导出工具；③ 冒烟与等价性脚本；④ 全量引用扫描。9/19 五轮空转的全部代价，本质上是先动手改、后建立观测。
你怎么把这套东西教给学员 / 带团队？不直接给答案，给可复用的判断顺序：先复述现象不翻译 → 枚举现场对象 → 全量映射核对 → 一条观测证明 → 才看时序 → 最小修复 + A/B → 固化成校验 / 冒烟 / 纪律。每次事故都转成一条带「为什么」的纪律（不是禁令），并把「勿再沿用」的回退清单公开，让新人知道哪些坑已经踩过。
