二、10003 三连斩的时序

动画归一化进度 0 → 1 上，伤害段的时机由 CSV 的 SegTimings = 0.3;0.6;0.9 定义；出手特效走另一条独立时间轴，时机来自 CastEffectTimings，与伤害段无关。AttackState.OnUpdate 每帧读一次 normalizedTime，两条轴各自比对。

0.0 起手0.51.0 动画结束
特效与伤害段已经解耦。

P4 之前刀光是伤害的附属品：数量必须等于段数，时机写死成 SegTimings[i] − 0.05，结果因为早于本段伤害触发、读到的 m_SegIdx 还是上一段（首段为 0），被 PlayCastEffect 的守卫全部拦下 —— 一件都播不出来（原隐患 #1，已修复）。

现在是两条平行的时间轴，各自独立推进：CastEffectTimings 给时机、AttackEffectID（CSV 列 22）给特效 id，按下标配对。3 段伤害配 4 个特效也可以，位置随便放，甚至可以让同一个特效在多个时间点重复播出。

2026-09-15 去重 原先还有一个语义完全相同的 CastEffectIds 列（列 24），与 AttackEffectID 都是「出手特效 id 集合」。两列并存会导致「策划填 A、程序读 B」，已整列删除，特效 id 的唯一来源是 AttackEffectID。

规则：不配时机就不播。

实际播放条数 = min(特效 id 数, 时机数)。CastEffectTimings 留空意味着该技能一件出手特效都不播，系统会打出 [SkillData] 警告指名是哪个技能 —— 这里刻意放弃了「没配就按 −5% 推算」的兜底：刀光缺席一眼可见，而时机错位要对着设计稿逐帧比对才能发现。

三、数据流转四层

配置层一次性加载后只读；数据层持有战斗实体与技能实例；控制层每帧驱动；表现层既接收输出，又反向提供推进信号。

↓ 写入参数　↑ 回读状态

三条数据主线

  • ▸下行（配置 → 运行时）：CSV 在 SkillDataManager 里解析成字典，Skill 构造时拿走 BaseData 引用，此后全程只读。配置与状态严格分离。
  • ▸横向（实体之间）：不走事件总线，是直接方法调用 —— 攻击者的 Skill 持有受击者引用，直接 target.OnDamaged(...)。受击特效 id 由攻击方按段号算好后随调用传入（Skill.GetHitEffectIdForSegment），受击方不反查攻击者的任何字段。
  • ▸上行（表现 → 控制）：FSM 反向依赖 Animator —— 写入 SkillId 推动动画，再回读 normalizedTime 决定何时触发伤害、何时切回待机。

五、状态机转换表

CombatStateMachine 用 Dictionary<CombatState, HashSet<CombatState>> 维护合法边，CanTransitTo() 拦截一切非法跳转。行是源状态，列是目标状态。

Move 状态目前是孤岛。

它在 InitStateMachine() 里注册了，但全工程没有任何一处 RequestState(CombatState.Move)。追击走的是 m_NeedMoveTarget → MoveTarget() 直接调 NavMesh，绕过了状态机。

段推进仍用 if 而非 while。
