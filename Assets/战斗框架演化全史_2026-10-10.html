03

起点：基线评估与 FSM 接入

2026-09-03 / 09-07
第一次全面体检：24 → 31 个脚本通读 09-03 产出《战斗框架分析报告》
痛点

框架已经能跑，但没人说得清它到底缺什么。三代体系并存：GEN1 Legacy（全局命名空间）、GEN2 Buff（BattleFramework.Core）、GEN3 FSM（StateMachine），只整合了一部分。想改任何一处，都要先有基线。

做法

通读全部脚本，按「会不会静默出错」给缺陷分级。优点记下来：数据/控制分层、CSV 配置驱动、事件驱动、索敌策略丰富；BufferSystem/（ulong 位枚举 + 零 GC 对象池）质量最高，被定为后续重构的标杆。

  • 🔴 P0：CombatUnit.m_Rage 被误设成 static（全服共享怒气）、StringConst 混入大量 UI/业务常量
  • 🟠 P1：大量空 Stub（受击/眩晕/浮空/击退全未实现）、无正式状态机、CSV 解析无边界校验 + EffectMsg 切分 Bug、新旧两套 Buff 未打通
  • 🟡 P2：每帧 OverlapSphere、命名拼写错误、死代码、单例非线程安全
为什么

分级的判据不是「严不严重」而是「会不会静默出错」。会崩的 bug 反而好办，最贵的是「配了但没反应」「跑了但算错」这类不报错的。这条判据后来贯穿整个项目，最终沉淀成工程铁律第 5 条（禁止静默降级）。

踩坑

CombatUnitController.cs 被上一轮失败的 Python 补丁脚本写坏：行尾变成双 \r\r\n（953 行出现孤立 CR），Update() 被嵌套 if 双重污染。修法是 decode('utf-8-sig').replace('\r','') 归一行尾 → 按精确行号重写 → 回写 BOM + CRLF。这是「改 .cs 一律走带断言的 Python 脚本」这条铁律的起源，后来又因此吃过三次亏。

第一阶段 FSM 接入：让「单位当前处于什么状态」有唯一答案 09-03 编译 0 Error / 0 新增 Warning
痛点

没有正式状态机。OnDizz/OnHitOut/OnAddBuff/ImmedDamage/HitBack 等受击回调全是空实现，「单位是不是在眩晕」这个问题散落在若干个 bool 里，谁都能写、谁都写不全。

做法

新建 Scripts/BattleFreamwork/StateMachine/ 三个文件：

  • CombatState.cs：枚举 Idle/Move/Attack/Stun/Silence/Knockback/Dead + ICombatState 接口
  • CombatStateMachine.cs：注册 / 转换合法性校验 / ChangeState / Tick；Dead 为终态，受控态结束回 Idle
  • CombatStates.cs：7 个状态类实现

Controller 侧新增 m_StateMachine、CurrentState、IsSilenced，Start() 调 InitStateMachine()，Update() 收口为 m_StateMachine.Tick(Time.deltaTime)。打通受击事件：OnDamaged(Hp<=0)→Dead、OnDizz→Stun、OnHitOut/OnAirHit→Knockback、新增 OnSilence→Silence。

为什么

这是所有后续改造的地基。后面每一次「段号在哪推进」「受击要不要进状态机」「Buff 怎么仲裁控制」，争的都是「谁有资格回答单位当前处于什么状态」。先把这个答案收敛成一个地方，后面才吵得起来 —— 也才吵得清楚。

深度评估 + Phase C：Buff↔FSM 整合 09-07 成熟度 4.6 → 5.4 / 10
痛点

Buff 系统自己有一套控制倒计时，FSM 也有一套，两套互不映射。控制效果的时长、叠加、免疫、驱散没有唯一真相源 —— 眩晕 3 秒到底是 Buff 说了算还是状态说了算，没人知道。

做法

改 4 个文件：

  • Controller 加桥接层：HasHardControlBuff/HasSilenceBuff/IsControlBuff/SyncControlStateFromBuffs/OnControlBuffAdded/OnControlBuffRemoved；OnDizz/OnSilence 改为 AddBuff(Stunned/Silenced) + 覆盖时长，不再 直接 RequestState(..., time)
  • StunState/SilenceState 删除自计时字段，改为每帧查询 Buff；KnockbackState 保留自计时（瞬时硬直，不是 Buff）
  • 转换表补 3 条边：Stun→Silence、Knockback→Stun、Knockback→Silence
  • BufferData.csv 补 1005 Stunned / 1006 Silenced 两行 —— 原表只有 4 个 Buff
为什么

Buff 是唯一真相源，状态只是投影。优先级定为 硬控（Stunned/Frozen/Petrified/Sleeping） > 沉默 > 回 Idle。时序上天然正确：Update() 先跑 BuffSystem.Update()（到期 → 移除 → OnBuffRemoved → SyncControlStateFromBuffs → 切状态），再跑 m_StateMachine.Tick()。

顺带修正了 09-03 的一次判断失误：Skill.ImmedDamage 是空桩意味着「技能无法扣血」，应从 P1 升为 P0 —— 这是当时最致命的一条。

验证

成熟度 4.6 → 5.4；缺陷数 P0 4→3、P1 9→6、P2 7→8。十维评分：架构 4 / 数据 5.5 / 控制 7 / FSM 8 / 技能 3 / Buff 9 / 事件 5 / 配置 4.5 / 表现 5 / 测试 3 —— 技能 3 分是全项目最低，精准预言了后面大半年的工作方向。

04

段号驱动：四轮返工（v1 → v4）

2026-09-11 → 09-14

这是全项目返工最集中的一段，也是教训最值钱的一段。核心命题只有一个：一个三段技能，怎么知道现在打的是第几段？

方案 A：动画事件只传 skillId，段号靠顺序计数器 09-11
痛点

多段攻击需要识别段号。前一天的方案是「动画事件多传一个 segIdx 参数」，被用户明确否定：动画事件只传 skillId，其余自己推。用户的原话约束后来被反复引用 —— 动画资产是美术的，不该为程序逻辑多背参数。

做法

Skill.cs 新增 m_SegIdx、BeginNextSegment()（含 60 帧超时兜底）、ResetSegIdx()，SetSkillCaster 入口自动 Reset。OnDamaged 改用 attacker.m_CurSkill.SegIdx 索引 HitEffect[segIdx-1]。

为什么

m_SegIdx 放在 Skill 类而不是 Controller：Skill 实例生命周期 = 一次技能释放周期，对象池复用时 SetSkillCaster 自然重置。这样 OnDamaged 直接读即可，避免在 SkillHit → HitTarget → ImmedDamage → OnDamaged 四层方法签名上穿透参数。

⚠ 这个「自然重置」的假设在下一轮就被证伪了。

v2：SetSkillCaster 每次都重置，三段永远只看到第 1 段 09-11 09:25 用户当场指出
痛点

用户原话：「一个技能整个播放过程中要多次调用 OnSkillCase，每次调用都执行 Skill.SetSkillCaster，而每次调用你都重置了攻击次数记录，那这样完全不对吧」。

做法

两层修复：① SetSkillCaster 移除 ResetSegIdx()；② OnSkillCase 入口加 isNewExecution 检测 —— 新字段 m_LastOnSkillCaseSkillId / m_LastOnSkillCaseFrame / 阈值 30 帧，条件为「skillId 变了 或 帧间隔 > 30」。

为什么

教训：「在哪里加新逻辑」之前必须看完整调用链。SetSkillCaster 看似「新技能」入口，实际是 OnSkillCase 每次事件都会调的上下文设置，把重置放这里是反模式。任何「重置」操作都要先确认它的调用频率是「每次」还是「每次新一次」。

v3：30 帧阈值让多段识别整体失效 09-11 10:45 → 11:50 先误判后订正
痛点

用户再跑一遍：「还是输出 1」。复核发现：三段技能事件间隔 0.6s = 36 帧 > 阈值 30 ⇒ 第 2、3 段都被误判成「新一轮执行」而 Reset ⇒ 永远只看到 segIdx=1。只要段间隔 > 0.5 秒，所有段都退化成第 1 段 —— 而 0.5s 是动作游戏极常见的段间隔。

做法

删除 Controller 层 isNewExecution 三字段与判断；BeginNextSegment 超时改用 Time.time、阈值 3 秒（纯异常保护）；保留 IdleState.OnEnter → ResetSkillSegIdx() 为唯一主重置点。

为什么
  • 「段间隔 > 阈值」不是「新一轮执行」的可靠信号 —— 动作游戏段间隔可长可短，任何帧/秒阈值都会误伤
  • 真正的「新一轮」信号是 FSM 状态转换（Attack 无自环 → 必过 Idle → 转换点才是归零点）
  • 同一种「重置职责」在多处冗余实现 = 必然有 bug。当时有 3 道重置关互相打架，精简到 1 道反而可靠
踩坑

11:35 我先推断「动画事件没绑」—— 这是错的。模型扫描的 events 字段为空不等同于没绑。Skill.cs:174 的 Debug.LogError(m_SegIdx) 能出 ⇒ OnSkillCase 至少回调过一次。真因是 30 帧阈值。教训：不要用「扫描结果为空」直接下「没有」的结论。

v4：连放技能输出错乱 —— 主重置点根本没被触发过 09-11 下午 最关键的修复
痛点

用户原话：「如果玩家持续连续释放当前技能，那么输出的结果就不对了」。

做法

两条根因，缺一不可：

  • 根因 A：grep 全工程 RequestState —— 没有任何地方调 RequestState(CombatState.Attack)。_currentState 从构造起一直是 Idle，IdleState.OnEnter 只在 InitStateMachine() 跑过一次 ⇒ v3 定的「唯一主重置点」是死代码
  • 根因 B：NYT.controller 的 Idle 状态上挂着 SkillId == 10003 → Skill10003 转换，技能播完沿 exitTime 回 Idle 时 SkillId 仍残留 ⇒ 条件立刻再成立 ⇒ 技能自动重放，段号继续往上爬（第 1 次 1/2/3，第 2 次 4/5/6）

后果链：SegIdx 跨释放累加 → OnDamaged 的 segIdx <= hitEffects.Count 守卫失败 → 掉进 else 分支 → 每次命中把整个特效列表播一遍。

修法：BattleConst 加 ani_IdleState = "Idle"（⚠ 控制器里 Idle 是状态名，ani_IdleC("IdleC") 是片段名，原来的 IsUseAttSkill 拿片段名比状态名，永远 false）；新增 IsAnimatorInIdleState；StarSKill 动画真正播放后 RequestState(CombatState.Attack)；AttackState 补两段式判定 + 5 秒保险丝。

为什么

为什么必须两段式判定：SetInteger("SkillId", 10003) 后 Animator 不会立刻切状态（Idle 那条转换带 m_HasExitTime: 1 / m_ExitTime: 0.84），这一两帧内 IsAnimatorInIdleState 仍为 true。若进 Attack 当帧就判「播完了」，IdleState.OnEnter 的 ResetSkillId() 会把 SkillId 清 0 —— 那条还没生效的 Idle→Skill 转换条件就永久不成立，技能根本播不出来。

对上一轮「关键学习」的修正：「Attack 无自环 → 必过 Idle」只对了一半 —— 转换表只定义「允许怎么走」，不保证运行时真的这么走，必须同时确认有代码在调 RequestState(Attack)。验证设计假设时，要顺着调用方 grep 一遍，而不是只读转换表。

遗留

顺带查出：SetCd(Skill) 是空实现 ⇒ 普攻完全没有 CD 拦截（v2 时记的「冷却拦截保护」记反了，是根本没有保护）；IsUseAttSkill 是永远 false 的死代码。

v4 落地 + 清理：双路并存导致伤害翻倍 09-14 段推进 t=0.303/0.601/0.901
痛点

v4 方案（段号判定放进 AttackState.OnUpdate，用 normalizedTime 推进，段数/时机从 CSV 读）需要落地。首轮 Play 只跑到 10003 一轮 GBL 就被打死、且 GameStart 无 respawn ⇒ v4 路径没机会跑。

做法

5 个文件（备份 .bak.2026-09-14-fsm-driven）：AttackState 完全替换、Controller 加 TriggerSegmentHit/GetCurrentAnimatorStateInfo/GetWeaponAnchor、Skill.SegIdx 改可读写 + PlayCastEffect、SkillData 加 SegTimings/CastEffectIds/HitEffectIds（列 23/24/25）。

验证阶段临时给 GBL 加 5 行「不死」代码（if (gameObject.name.Contains("GBL") && Hp <= 0) Hp = 1;），跑通后必须删除。清理阶段还做了三件事：删不死代码、删 [DIAG] 日志、注释掉 OnSkillCase 里的 m_CurSkill.SkillHit()。

为什么

旧的 OnSkillCase 反射路径与新的 AttackState 都会调 SkillHit() ⇒ 伤害被两条路径同时触发。v4 落地时刻意不删 OnSkillCase（作为兼容路径保留），清理时才收口。

验证

用数值落差反证：清理前 GBL 单次三段伤害约 26000（双路各打一次），清理后 13063（单路独占）。段推进 t=0.302/0.602/0.901，与 CSV 配置的 0.3/0.6/0.9 精确吻合。

这一段沉淀的方法论（用户原话）

用户在 09-12 的方案评审中给了三条关键提示，后来被反复引用：
① 「下一步做的事也是错的」 —— 当用户否定时，先承认错误再追问「你想要的是什么」，而不是继续推销原方案；
② 「对于类似 RPG 类型的游戏，一般玩家的技能特效都是怎么进行管理的」 —— 先确认当前架构已有的能力，再决定是补缺还是改架构；
③ 「10 个玩家 × 5 个技能 × 5 段」 —— 用具体数字量化痛点，让规模化问题具象化，比泛泛说「工作量太大」有力得多。

反查表该放哪（用户追问后定案）：独立静态类，由被注册的 Controller 自己注册/注销，Buff 模块只做查询。核心原则一句话：谁被注册，谁负责维护索引。现在是反过来的 —— Buff 组件在 Setup 里替所有 Controller 建索引，Controller 自己压根不知道自己被登记了，这正是「感觉不好」的第二层病因。

四个好处：① 生命周期最可靠（Controller 是 MonoBehaviour，Start/OnDestroy 天然成对，P14 那颗「没有 OnDestroy 兜底」的雷自动消失）；② 与数据重绑解耦（CurCombatUnit 换人触发 Rebind，但实例 ID 不变 ⇒ 表项压根不用动）；③ Buff 模块变纯读方 ⇒ 换实现/上服务器/做 NullBuff 都不再牵动全局；④ 换网络 ID 只改一处。

两步走：先做静态类 + 自注册（项目里确实还没有「战斗上下文」这一层，静态不是妥协）；等 S2 联网或需要多沙盒单测时，再升格为 interface IUnitRegistry + 实例注入 —— 因为读写职责已分清，升级时调用点一行不改。

必须知道

反查表的作用 = 「身份证号 → 人」的翻译器：Buff 里只存施加者的 int 编号，DoT 每跳结算时要把它翻译回 Controller，否则这刀伤害不知道算在谁头上。它决定五件事：击杀归属、仇恨与反击、受击朝向、伤害统计、生命周期安全。
⚠ 三颗雷：① GetInstanceID() 不能跨端（接状态同步必然失效，得换 entityId）；② 注销只挂在 OnDestroy 上；③ 全局静态表跑不了两个独立战斗沙盒。

Animancer 接入可行性（方案阶段，未实施） 10-10 等用户拍板三件事
痛点

项目已经分离了战斗显示层，显示层能否接入动画插件 Animancer。

做法

三条好消息已核实：① 装的是 Animancer v7.4.2 Lite；② Animancer.asmdef 写了 "autoReferenced": true，项目脚本走默认 Assembly-CSharp ⇒ 直接 using Animancer; 就能编过，不用改任何程序集引用；③ prefab/场景里零接入，迁移是纯新增。工程里还带了官方的 HybridAnimancerComponent（与 AnimatorController 共存）。

为什么

★ 最关键的一条：09-28 抽的 ICastClock，正好就是 Animancer 的接入点。当时注释写的是「服务器没有 Animator，一次施法永远不会推进段号」，现在同一个接口换用途即可 —— 全工程只有 AnimatorCastClock 一处读 View.StateInfo，换时钟，AttackState 一行都不用改。这就是当初那次「提前付定金」的回报。

⚠ Lite 版三道硬门槛：无 AnimancerState.Speed（顿帧大概率保不住）、无 Layers/Mask（受击无法只播上半身）、无 Mixers（八向移动混合做不了）、自定义淡入恒 0.25s。最狠的一条是官方明示的：Lite 在 Editor 里全部功能都能跑，运行时构建才退回默认行为 ⇒「我测了没问题」这句话在这里不成立。

顿帧的救法（应顺势升级）：现在顿帧是 Animator.speed = 0，Animancer 接管后很可能不再生效，Lite 又没有 state.Speed ⇒ 建议把顿帧升级成时钟层的概念（顿帧 = ICastClock 不推进），这样与底层动画系统都无关，联网时也天然正确。

🚫 明确不建议：拿 Lite 自带的 Animancer.FSM 替换战斗 FSM —— 战斗 FSM 里塞了 Buff 仲裁、段号推进、打死 Arch 等语义，与 CanEnterState/CanExitState 是两套转换哲学，换过去等于把稳定的东西重做一遍。

七条设计原则的诞生

贯穿全程

这些原则不是事先定好的，每一条都是某次事故或某次返工之后才被总结出来的。括号里是它的诞生场景。

01

单一真相源

诞生于：P6 SegCount（时机点个数 ≠ 段数）、P5 定稿（Str2IntList 假告警）、Buff Id 主键

同一个事实只能有一个地方定义。SegTimings.Length 不能兼当段数，CastEffectIds 与 AttackEffectID 不能两列并存，Buff 的「身份」不能既是 Type 又是 Id。每次发现「两个地方都能回答同一个问题」，就意味着其中一个必然是错的。

02

显式优于隐式

诞生于：P5 用户拍板删 −5% 推算、P10 删 m_CurSkill 反查、P16 段号显式传参

用户那句话是最好的注解：表现缺位一眼可见，时机错位要逐帧比对才能发现。同理，「靠注释守护的调用顺序」（P16）、「靠反查攻击者字段拿段号」（P10）、「靠 Animator 残留参数判断状态」（v4 根因 B）—— 凡是只能靠注释或巧合成立的东西，迟早会错。

03

结构优化 ≠ 性能优化，不许混着报

诞生于：P11（性能 ≈ 0）、P9（装箱仅 24B）、索敌 NonAlloc（当前零收益）

删 object context、删 owner 形参、把 OverlapSphere 改 NonAlloc —— 每一次都如实标注真实收益。P11 明写「性能 ≈ 0，这是结构优化不是性能优化」；NonAlloc 改造后明写「改的三个方法零调用点，是预埋」。这条自保机制让后来每一次「要不要做」的判断都有真实依据，而不是被「听起来很厉害」带跑。

04

fail-fast 优于静默降级（工程铁律第 5 条）

诞生于：09-03 缺陷分级判据「会不会静默出错」；09-18 契约校验前移；P20 ValidateEffectIdContract

资产漏配 → 构造期 LogError 指名；特效 id 撞车 → 加载期 LogError；配了效果 2 却没有 BuffID → LogError；缓冲区溢出 → LogError。禁止为「资产不一致」写运行时静默降级 —— 静默降级会把「配错了」伪装成「打了没反应」，让排查成本暴涨（2003 撞车就是这句话的反面教材）。

05

需要注释守护的顺序 = 内聚不足

诞生于：P16 SkillHit(segIdx)

「先写 SegIdx 再调 SkillHit()，顺序绝不能颠倒」—— 这句话在四个文件里各写了一遍，本身就是病。正确做法是把顺序收进类型系统：SkillHit(int segIdx) 唯一入口 + { get; private set; }，让「顺序错了」编译不过。

06

转换表只定义「允许怎么走」，不保证运行时真这么走

诞生于：v4 根因 A（全工程零个 RequestState(Attack)）

v3 把「段号归零」寄托在 IdleState.OnEnter，而它从来没被触发过 —— 因为根本没人切进 Attack。验证设计假设时，要顺着 RequestState 的调用方 grep 一遍，而不是只读转换表。同理可推广到任何「规则表 + 运行时」的组合。

07

视觉 bug 先枚举现场对象，不许翻译成时序假设

诞生于：2003 撞车（五轮排查全打在时序上）

用户原话：「你给我描述问题的时候你没有真正理解我的问题」、「你不会识别游戏画面，你仅仅靠日志来进行分析」。
铁律：① 视觉描述不许自行翻译，先复述确认；② 我看不到画面，必须主动要截图（我读得了图片）；③ 拿不到图就跑「Dump Effect Objects」看对象归属（画面上现在有几个对象、各自叫什么、挂在谁身上）；④ 最后才碰日志与时序。
配套：探针里任何「不该出现却出现了」的字段就是主因，优先级高于任何推理。
