## 3. C 类：架构层收敛（≈ 102 行）

这一层不是「找零散死代码」，是「这个结构本身能不能更薄」。

### C1. `CombatUnitController` 的 Facade 转发层 —— 7 个方法 / ~60 行

`L579-707` 有 7 个方法（`OnDamaged` / `OnHeal` / `OnHitOut` / `OnPlayerAirHit` / `OnAirHit` / `OnDizz` / `OnSilence`），**函数体全部是「判空 → 转发给 `m_HitReaction`」**。

注释给的理由是「调用方一行都不用改」「将来二十个技能效果桩统一认识 Controller 这一层」。但实测调用方只有：
- `Skill.cs:487` → `OnDamaged`
- `UnitBuffComponent.cs:242` → `OnDamaged`

**2 个调用点。** 其中 `OnPlayerAirHit` / `OnAirHit` / `OnHitOut` 三个的调用方是**空的技能桩**（见 B3），`OnHeal` 也是空桩。

- `shrink:` 让 `Skill` / `UnitBuffComponent` 直接调 `Owner.HitReaction.ApplyHit(...)`，删掉这 7 个转发方法。
  - 收益：-60 行，且 `Controller` 只剩「数据 + 决策 + FSM 桥接」，投影边界从**三层变两层**（View / Reaction / Controller）。
  - 成本：改 2 个调用点。
  - 反驳意见「将来 20 个桩要对接」：那时候它们对接的应该是 `UnitHitReaction`，而不是一个再包一层的 Controller。**Facade 只有在「调用方多到改不动」时才值钱；现在调用方是 2。**

### C2. `CombatStateMachine` 的四个字段 —— 12 行

`_owner` / `_previousState` / `PreviousState` / `OnStateChanged` 四个成员**全部零使用**。类注释里作者已经预判了这一点（「若确认长期不用，可以连同构造函数参数一起删除」）。
- `delete:` 四个成员 + 构造参数，`CombatStateMachine()` 变成无参构造。

### C3. `BuffSystemPooled` 的四个「收集 → Drain」方法 —— ~30 行

`RemoveBuff`(死) / `DispelNegativeBuffs` / `DispelAllBuffs` / `ClearAllBuffs` 四个方法各自抄了一遍同样的骨架：
```
_pendingRemove.Clear();
for (...) { if (谓词) { _pendingRemove.Add(x); count++; } }
DrainPendingRemoves();
```
- `shrink:` 收敛成一个 `RemoveWhere(Predicate<Buff> match)` + 三个一行谓词。同样的行为，-30 行，且下次加「驱散增益」时不用再抄第四遍。

### C4. 架构层总体判断：**框架本体不臃肿**

必须说清楚，免得上面那张长清单给人错误印象：

✅ **值得保留的复杂度**（不要动）：
- `UnitView` / `UnitHitReaction` 的拆分 —— 把「画面改写」和「数值/决策」分开，构造注入 + `readonly` 字段，这是**降复杂度**的改动，不是升。两个类各 ~200 行，注释密度 46% 但都解释了「为什么不是别的做法」。
- `CombatStateMachine` 的转换白名单表（`L39-82`）—— 显式声明式，比散落的 `if` 更好读。
- `AttackState` 的双游标（`_firedSegIdx` 伤害轴 / `_castCursor` 特效轴，`CombatStates.cs:L45-368`）—— 两个概念确实解耦了，代码长但结构诚实。

- `BuffSystemPooled` 的重入防护三件套。
- `ClassObjectPool` 的 `#if UNITY_EDITOR` 重复回收检测 —— 就是 ponytail 说的「最小自检」，保留。

### C5. 注释里的「考古层」—— 32 行，建议改形态而非删除

`Assets/Scripts` 里 2,732 行注释（占 31%），其中约 32 行是**在描述已经不存在的代码**：

- `shrink:` 这 32 行搬去**变更记录**（项目已有 `Assets/战斗框架修改记录_*.md`）。留在代码里的代价是：新读者读到「这里删过 X」，然后花时间确认 X 是不是真的没有了 —— 而 changelog 里读到的是一样的信息，且不会让人对着当前代码困惑。
